# 雷區規則撰寫規範

給要新增／更新 `.cursor/rules/*.mdc` 雷區規則的人（AI 或工程師）。目的：同一個地基問題不要出現第三次。

## 什麼時候必須寫（或更新）一份雷區規則

- 同一個問題「改好又被改壞」，或「反覆出現」超過一次
- 修復耗費不少時間排查根因，未來很可能再踩（尤其是跨檔案、跨 async 生命週期的隱性耦合）
- 修完後，任務結束前就要寫，不要留到下次——下次通常是同一個坑再炸一次才想起來

## 檔案位置與命名

- 放 `.cursor/rules/`，命名 `<領域>-invariant.mdc` 或 `<領域>-invariants.mdc`（多條不變量用複數）
- 純粹「AI 執行時的禁止/正確條列」放這裡；長篇規格／交接文件放 `docs/`，並回頭更新 [docs/README.md](./README.md) 索引

## Frontmatter

```yaml
---
description: 一句話症狀（給規則選擇器看，越具體越好）
globs: 逗號分隔的檔案路徑或 glob，只在這些檔案被讀取/編輯時才自動載入
alwaysApply: false
---
```

- `globs` 與 `alwaysApply: true` **二選一，不可同時設定**
- 只有真正「不管改哪個檔案都可能踩到」的規則才用 `alwaysApply: true`（精準、不准丟資料、退路須同意、popup 分級、繁中等）；其餘一律用 `globs` 限定相關檔案，避免規則庫變大後拖慢每次對話
- 新增規則後，同步在 [.cursor/rules/00-pitfall-index.mdc](../.cursor/rules/00-pitfall-index.mdc) 加一行索引（規則檔名／症狀關鍵字／對應檔案）

## 內容六段式結構

```
# 標題（一句話講清楚是什麼雷區）

## 症狀
怎麼發現的、使用者／老師／學生看到什麼現象。用實際畫面文字、錯誤訊息，不要只寫抽象描述。

## 根因
程式碼層級的解釋，附檔名＋行號引用。說清楚「為什麼」會這樣，不是只講「哪裡壞了」。

## 不變量
用「有這把鑰匙，就做這件事」寫出改動後必須永遠成立的條件。挑選目標，不要消去法（沒 A 就 B、先列一堆不可能）。

## 禁止
❌ 反例程式碼片段，越具體越好（哪個函式、哪一行邏輯）。

## 正確
✅ 對照的正確做法程式碼片段。

## 實測
列出重現／驗證步驟，讓下次改動的人知道怎麼確認沒有踩雷。
```

現有規則（如 [material-snapshot-refs-invariant.mdc](../.cursor/rules/material-snapshot-refs-invariant.mdc)）已大致遵循此結構，新規則請對齊，不要漏段落。

## 修改前自問（每份規則最後一段的慣例）

在文件結尾加一段「改動前自問」或「改動前自問清單」，列出「若要動到 XX／YY／ZZ 檔案，請先確認 OO 是否仍成立；若否，停下」。這是目前規則庫裡最有效的一段，能在下手改程式碼**之前**攔住問題，而不是改完才發現。

## 與 PR 模板的關係

[.github/PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md) 有一條通用 checklist：「本次改動是否命中任何雷區規則／是否修了重複坑卻沒補規則」。寫完規則後，之後的 PR 應該勾得起來，不是寫完就丟著沒人記得看。
